# AI 决策情报网站：后端、数据来源与自动化可行性分析

> 文档状态：V1.0
> 范围：不包含会员、付费墙、订单与支付
> 目标：明确哪些功能可实现、依赖哪些后端能力、数据从哪里来，以及 Codex 定时任务如何参与数据采集与更新。

---

## 1. 结论摘要

项目整体可行，首版不需要昂贵的数据授权或复杂实时系统。最合理的产品形态不是“爬虫直接发新闻”，而是：

```text
官方/开放数据源
→ 定时采集
→ 原始数据归档
→ 去重与实体识别
→ Codex 提取事实、翻译、归类、评分和生成候选摘要
→ 编辑审核
→ 内容发布
→ 网站、搜索、RSS、Newsletter
```

可行性的关键不在抓取数量，而在四件事：

1. 建立可追溯的来源目录。
2. 把“候选事件”和“已发布内容”分开。
3. Codex 负责研究与编排，后端负责稳定存储和对外服务。
4. 重要内容保留人工审核，避免把模型判断直接当作事实发布。

### 推荐首发边界

- P0 先接入 20～30 个经过合规复核的高价值来源；运行稳定后再扩展到 30～50 个，而不是全网抓取。
- 每天采集约 100～300 条候选记录。
- 去重后保留约 20～40 个候选事件。
- 最终发布 5～12 条快讯和 1 期日报。
- 自动更新结构化事实；观点、重大新闻和深度文章由人审核。

以上数量是产品容量假设，需要上线后根据编辑处理能力调整，不是行业基准。

## 2. 系统角色划分

### 2.1 Codex 定时任务负责

- 按计划触发采集脚本或研究任务。
- 检查来源是否出现新增或变化。
- 对新增内容做初步筛选、翻译、摘要和结构化提取。
- 识别可能重复的事件。
- 为事件建议主题、实体、重要度和可信状态。
- 生成日报草稿、来源缺失报告和数据异常报告。
- 在任务失败、来源结构变化或结果异常时提示维护者。

OpenAI 官方公开的 Codex 用例把自动化、资料更新、数据清洗和可重复工作流列为适合场景；据此可以把 Codex 用作本项目的研究与运维编排层。[OpenAI Codex Use Cases](https://developers.openai.com/codex/use-cases)

### 2.2 Codex 定时任务不负责

- 直接承载网站访问请求。
- 充当生产数据库。
- 保证秒级实时更新。
- 保存唯一一份原始数据。
- 在无人审核情况下自动发布高风险新闻。
- 替代后端的权限、搜索、缓存、邮件发送和监控。

### 2.3 网站后端负责

- 原始数据、事件、来源、文章和版本的持久化。
- 对前台提供内容列表、详情、主题、搜索和订阅接口。
- 管理内容审核、发布、撤回和更正状态。
- 保证任务幂等、失败重试、日志和审计。
- 管理用户、Newsletter 订阅、收藏和关注。
- 为 Codex 定时任务提供稳定的导入命令或内部接口。

## 3. 后端功能架构

```text
┌──────────────────────────────────────────────────────┐
│                    公共网站                           │
│ 首页 / 最新 / 日报 / 文章 / 主题 / 搜索 / Newsletter │
└───────────────────────┬──────────────────────────────┘
                        │ 内容读取与用户操作
┌───────────────────────▼──────────────────────────────┐
│                   应用后端                            │
│ 内容服务 │ 搜索服务 │ 订阅服务 │ 账户服务 │ 媒体服务 │
└───────────────┬─────────────────┬────────────────────┘
                │                 │
┌───────────────▼──────────┐  ┌───▼────────────────────┐
│      编辑与审核后台       │  │   数据采集与处理管线    │
│ 候选池 / 审核 / 发布 / 更正│  │ 抓取/解析/去重/评分/归档│
└───────────────┬──────────┘  └───┬────────────────────┘
                │                 │
                └────────┬────────┘
                         ▼
              数据库 / 搜索索引 / 对象存储
                         ▲
                         │
                  Codex 定时任务
```

### 3.1 内容服务

支持快讯、日报、分析、主题、公司、产品、模型和来源。必须具备草稿、审核中、定时发布、已发布、已更新、已撤回状态，并保留修改历史。

### 3.2 采集服务

每种来源使用独立连接器。连接器只负责获取和规范化数据，不负责决定是否发布。新增来源时不修改核心内容逻辑。

### 3.3 处理服务

负责正文清理、语言识别、时间标准化、内容哈希、相似度去重、实体识别、事件聚合、来源分级和候选评分。

### 3.4 编辑服务

编辑在同一页面查看原文、机器摘要、关联事件、重复项、来源级别和修改差异，然后选择发布、合并、延后或拒绝。

### 3.5 搜索服务

首版搜索标题、摘要、正文、主题和实体。搜索索引只收录已发布内容；撤回内容立即移出结果，但原 URL 保留说明。

### 3.6 Newsletter 服务

管理免费订阅、确认、退订、发送记录、退信和投诉。从已发布内容生成邮件，不让定时采集结果绕过编辑审核直接发送。

## 4. 核心数据对象

### 4.1 来源 `source_feeds`

- 来源名称、组织、来源等级。
- 类型：API、RSS/Atom、网页、GitHub、邮件、人工。
- 获取地址和解析规则。
- 抓取频率、时区和启停状态。
- 使用条款、robots、授权状态和归属要求。
- 最近成功时间、连续失败次数和健康状态。

### 4.2 原始记录 `raw_documents`

- 来源记录 ID、原始 URL、外部唯一 ID。
- 标题、正文或允许保存的摘要、作者和发布时间。
- 原始响应摘要、内容哈希和抓取时间。
- HTTP 状态、ETag、Last-Modified、解析版本。
- 原始记录不可被后续模型输出覆盖。

### 4.3 候选事件 `candidate_events`

- 规范化标题、事实摘要、事件发生时间。
- 关联公司、产品、模型、人物和主题。
- 来源集合和一手来源数量。
- 新颖性、影响力、可信度、可行动性评分。
- 机器置信度、风险标记和推荐动作。
- 状态：待处理、待审核、已合并、已拒绝、已发布。

### 4.4 已发布内容 `content_items`

- 快讯、日报或深度分析。
- 标题、导语、正文、作者、来源和主题。
- 发布、更新、撤回和更正信息。
- AI 辅助说明。
- 与候选事件和原始记录之间的可追溯关系。

### 4.5 实体 `entities`

- 公司、产品、模型、人物和主题。
- 中英文名称、别名、官网、Logo、简介和状态。
- 合并关系、来源和最后核验时间。

### 4.6 任务运行 `ingestion_runs`

- 任务类型、计划时间、开始与结束时间。
- 成功、部分成功、失败状态。
- 获取数、新增数、重复数、异常数。
- 错误摘要、重试次数和关联日志。

## 5. 数据源分级原则

### S0：官方且机器可读

API、RSS/Atom、官方 Release、结构化公告。可作为事实主来源，适合自动更新结构化字段。

### S1：官方网页

公司新闻室、产品博客、定价页、文档更新、状态页和政府公告。可作为事实主来源，但页面结构可能变化，需要监控解析质量。

### S2：可靠媒体与数据库

用于补充背景、采访和外部评价。除非有明确授权，不保存或重发完整正文。

### S3：社区与社交信号

用于发现线索和判断讨论热度，不能单独支撑“已确认”新闻。

### S4：匿名爆料与无法追溯内容

默认不采集；如保留，仅进入人工调查队列，不能自动展示在前台。

## 6. 推荐数据源目录

## 6.1 大模型与平台官方信息

| 数据源 | 获取方式 | 可获取内容 | 可靠性 | 建议频率 | 备注 |
|---|---|---|---:|---:|---|
| OpenAI News、官方文档和 Changelog | 官方网页/可用 Feed | 模型、产品、API、政策变化 | S0/S1 | 15～30 分钟 | 以官方发布时间和页面更新为准 |
| Anthropic News、Claude Release Notes | 官方网页 | 产品、API、模型和 SDK 更新 | S1 | 30 分钟 | Release Notes 信息结构清晰，[官方页面](https://platform.claude.com/docs/en/release-notes/overview) |
| Google Gemini API Release Notes | 官方网页 | API、模型上线、弃用和价格相关变化 | S1 | 30 分钟 | 官方 Changelog 可直接监测，[官方页面](https://ai.google.dev/gemini-api/docs/changelog) |
| DeepSeek News、API Docs | 官方网页 | 模型、API 与定价变化 | S1 | 30 分钟 | 新闻与文档需分别监测，[官方新闻](https://deepseek.com/en/news/) |
| Meta AI、Mistral、Cohere、xAI 等 | 官方博客/文档/GitHub | 模型发布、产品和 API 更新 | S1 | 30～60 分钟 | 首版按目标读者价值选择 10～15 家 |
| 国内平台：阿里云百炼、腾讯混元、百度千帆、字节火山引擎、智谱、月之暗面等 | 官方公告/文档/公众号人工补充 | 国内模型、产品、定价和政策 | S1 | 30～60 分钟 | 官网文档优先，公众号只保存链接和自有摘要 |

### 可行性判断

高。官方页面数量有限，适合建立白名单监测。难点是不同网站结构和动态渲染，需要“HTML 变化检测 + 语义判断”，不能只用 CSS 选择器长期裸跑。

| 数据源 | 获取方式 | 可获取内容 | 可靠性 | 建议频率 | 备注 |
|---|---|---|---:|---:|---|

| Hugging Face Hub | 官方 API/Webhook | 模型、数据集、Space、Model Card、下载趋势 | S0/S2 | 1～2 小时 | API 和 Webhook 可用，下载量是热度信号而非质量结论，[HF 文档](https://huggingface.co/docs/hub/en/api) |

高。数据结构化程度最好，适合自动生成“版本变化”候选事件。需要防止 Fork、镜像仓库和同名包造成误识别。

| 数据源 | 获取方式 | 可获取内容 | 可靠性 | 建议频率 | 备注 |
|---|---|---|---:|---:|---|
| arXiv | 官方 Atom API | 标题、作者、摘要、分类、版本 | S0 | 4～6 小时 | 官方 API 支持检索和分页，[arXiv API Manual](https://github.com/ArXiv/arxiv-docs/blob/develop/source/help/api/user-manual.md) |

### 可行性判断

中高。采集容易，选出真正影响产品和商业的论文较难。首版只覆盖 LLM、Agent、多模态、推理效率和 AI 安全等白名单主题，避免变成论文摘要站。

## 7. 数据采集策略

### 7.1 首选顺序

```text
官方 API / Webhook
→ 官方 RSS / Atom
→ Sitemap + 页面更新检测
→ 允许访问的网页解析
→ 人工录入
```

不以浏览器自动化模拟登录作为常规采集方案，也不绕过验证码、付费墙、访问限制或 robots 规则。

### 7.2 增量获取

- 使用外部 ID、URL、发布时间和内容哈希判断新增。
- 支持 ETag 与 Last-Modified 时使用条件请求。
- 页面内容变化时保存差异，不覆盖旧版本。
- 同一来源多次返回相同内容时不得重复创建候选事件。

### 7.3 去重

三层去重：

1. 精确去重：URL、外部 ID、内容哈希。
2. 规则去重：相同实体、近似标题、相近时间窗口。
3. 语义聚类：多个媒体对同一事件的报道归并为一个候选事件。

语义相似只能建议合并，涉及不同版本、不同融资轮次或不同模型名称时必须允许编辑拆分。

### 7.4 事件评分

每项 1～5 分：

- 来源可靠性。
- 事件影响力。
- 新颖性。
- 与目标用户的相关性。
- 可行动性。
- 多来源佐证程度。

评分只用于编辑排序，不直接替代编辑结论。前台若展示分数，必须公开评分方法。

## 8. Codex 定时任务设计

Codex 自动化建议采用“一个任务一个明确职责”，不要用一个超长任务处理所有来源。

| 任务 | 建议时间 | 输入 | 输出 | 失败处理 |
|---|---:|---|---|---|
| 官方源雷达 | 每 20～30 分钟 | 官方新闻、Release Notes、白名单 Feed | 新增候选事件 | 连续失败 3 次告警，不影响其他来源 |
| GitHub/HF 变化 | 每小时 | 仓库与模型白名单 | Release、模型卡、许可证或热度变化 | 记录限额并退避重试 |
| 论文筛选 | 每日 05:00 | arXiv 白名单查询 | 最多 10 条相关候选 | 超量时按相关性和新颖性截断 |
| 商业与监管监测 | 每 2～6 小时 | EDGAR、政府与交易所来源 | 披露和政策候选 | 高风险内容只进入人工审核 |
| 早间日报草稿 | 每日 06:30 | 过去 24 小时已审核事件 | 日报草稿，不自动发送 | 内容不足时生成缺口说明 |
| 晚间数据维护 | 每日 01:30 | 实体和来源目录 | 过期数据、失效链接、重复实体报告 | 不自动删除数据 |
| 周度来源审计 | 每周一 04:00 | 任务日志、来源健康度 | 失败率、噪声率和新增来源建议 | 由管理员确认来源调整 |

### 8.1 每次任务的标准输出

- `run_id`。
- 本次检查来源数。
- 新增、变化、重复和失败数量。
- 候选事件列表及来源。
- 不确定项和需要人工处理的问题。
- 是否触发告警。

### 8.2 幂等与恢复

- 相同任务重跑不得产生重复内容。
- 每个来源记录独立游标，部分失败不回滚其他来源。
- 写入前先保存原始记录，AI 处理失败时可重新执行。
- 每个候选事件保留生成它的任务版本和提示版本。
- 定时任务暂停或本地机器离线后，应能从上次成功游标继续。

### 8.3 运行环境判断

Codex 桌面自动化适合首版和内部运营，尤其适合需要浏览、判断和写入项目的任务。但它依赖当前配置的本地项目、主机可用性、凭据和权限，不应被视为高 SLA 云调度器。

因此建议：

- 验证期：由 Codex 定时任务触发仓库内采集命令或调用内部导入接口。
- 稳定期：机械化 API/RSS 获取迁移到后端 Job Runner；Codex 继续负责研究、语义判断、日报草稿和异常处置。
- 所有任务都通过同一个持久化接口写入数据库，保证以后更换调度器不改变数据模型。

## 9. 自动化与人工审核边界

| 能力 | 可自动执行 | 需人工确认 |
|---|:---:|:---:|
| API/RSS 拉取 | 是 | 否 |
| 原始数据归档 | 是 | 否 |
| 标题翻译和摘要草稿 | 是 | 重要内容需要 |
| 主题与实体建议 | 是 | 新实体或冲突需要 |
| 精确去重 | 是 | 否 |
| 语义合并 | 建议 | 是 |
| 官方版本与价格字段更新 | 可规则化自动 | 异常幅度需要 |
| 重要度和可行动性评分 | 建议 | 是 |
| 快讯发布 | 不建议首版自动 | 是 |
| 日报生成 | 生成草稿 | 是 |
| 深度分析 | 辅助研究和起草 | 是 |
| 政策、融资和争议信息 | 只生成候选 | 是 |

原则：自动化可以减少编辑阅读量，但不能消除新闻责任。

## 11. 编辑后台新增需求

在原页面需求基础上，后台必须新增：

### 11.1 候选池

- 按时间、来源、主题、实体、分数和状态筛选。
- 一屏对照原文、机器摘要和关联来源。
- 支持合并重复事件、拆分错误聚类。
- 支持批量拒绝低价值候选并填写原因。

### 11.2 来源中心

- 来源清单、等级、授权状态、频率和负责人。
- 24 小时/7 天成功率、平均新增量和噪声率。
- 页面结构变化和连续失败提醒。
- 一键暂停来源，不删除历史数据。

### 11.3 任务中心

- 查看定时任务最近运行、耗时、结果和错误。
- 支持安全重跑单次任务。
- 显示任务影响的候选事件。
- 不允许普通编辑修改凭据或调度配置。

### 11.4 实体消歧

- 处理同名公司、产品更名、模型别名和版本关系。
- 支持合并实体，并为旧 URL 保留重定向。
- 合并前预览受影响内容数量。

## 12. 版权、平台条款与内容保存策略

### 可以保存和发布

- 标题、作者、发布时间、URL、来源名等事实元数据。
- 为检索和审核所必需的有限摘录。
- 自己生成并经审核的摘要、分析、比较和结构化事实。
- 获得明确授权的数据和媒体。

### 默认不保存或不公开

- 其他媒体完整文章。
- 付费墙后的正文。
- 未经授权的图片、视频和图表原件。
- 通过绕过访问控制获得的数据。
- 平台条款禁止商业使用的数据。

### 来源展示

- 每条重要事实至少链接一个来源。
- 区分一手来源、官方来源、媒体报道和社区线索。
- 显示访问时间和数据核验时间。
- 原来源更新或撤回时触发复核。

## 13. 监控与质量指标

### 数据管线指标

- 来源成功率。
- 新增候选数和去重率。
- 解析失败率。
- 从来源发布到被发现的延迟。
- 候选进入审核的延迟。
- 编辑接受率和拒绝原因。
- 错误合并与错误实体率。

### 内容质量指标

- 有一手来源的内容占比。
- 每条内容平均有效来源数。
- 发布后更正率。
- 来源点击率。
- 收藏、分享和深度阅读率。
- 日报打开率和退订率。

### 告警条件

- 核心官方来源连续 3 次失败。
- 某来源 24 小时数据量异常增长 5 倍以上。
- 同一任务重复创建大量候选。
- 文章来源全部失效。
- Newsletter 退信或投诉突然上升。

## 14. 分阶段落地建议

### 阶段 A：数据闭环验证

- 建立首批 20～30 个来源白名单，并为扩展到 30～50 个预留连接器与运维能力。
- 打通采集、原始归档、去重、候选池、审核和发布。
- Codex 生成摘要与标签建议。
- 只做首页、最新、日报和文章详情所需数据。

验收：连续 14 天每天稳定产出，来源可追溯，重复和错误在编辑可接受范围内。

### 阶段 B：内容与搜索

- 增加主题、实体、全文搜索和 Newsletter。
- 建立来源中心、任务中心和内容更正流程。
- 根据编辑接受率淘汰高噪声来源。

### 阶段 C：结构化数据库

- 优先上线模型数据库，再做公司和产品档案。
- 将价格、版本、许可证和弃用日期做成可追踪字段。
- 增加关注和变化提醒。

### 阶段 D：规模化与迁移

- 将稳定的机械采集任务迁移到后端常驻调度。
- Codex 保留研究、异常处理、日报和周报草稿能力。
- 评估商业数据库和受限平台的数据授权价值。

---

## 15. 最终建议

首版后端应围绕“来源—原始记录—候选事件—已发布内容”四层模型设计。这比直接把抓取结果写成文章更重要，因为它决定了后续能否：

- 对同一事件聚合多个来源。
- 更新而不是重复发布。
- 解释每个结论从哪里来。
- 让 Codex、人工编辑和未来其他调度器共同工作。
- 在更换采集方式后仍保留完整历史。

最优先验证的不是全网覆盖率，而是：用首批 20～30 个高质量来源，能否连续 14 天稳定生产一份真正值得读的中文 AI 日报；验证通过后再扩展到 30～50 个来源。
